# CLAUDE.md

Guide pour Claude Code dans ce dépôt.

## Projet

Elongo : PWA de suivi de tontine, données partagées en direct via Supabase. JavaScript vanilla, sans build : `index.html`, `styles.css`, `config.js`, `backend.js`, `app.js`, `sw.js`, `manifest.webmanifest`, `vendor/` (supabase-js, jsPDF, autotable copiés localement pour fonctionner hors ligne), `supabase/schema.sql`.

## Commandes

- `npm start` : sert le dossier sur http://localhost:8080.
- `npm test` : `tests/e2e.mjs`, scénario séquentiel à deux onglets (organisateur + membre) en mode démo (le serveur de test renvoie une `config.js` vide, quel que soit son contenu). En cas d'échec il affiche l'état de chaque onglet. Playwright doit être résolvable (`npm i`).
- `npm run test:sql` : applique `schema.sql` deux fois sur un PostgreSQL local jetable et exécute `tests/rls-check.sql` (droits de chaque rôle).
- `npm run test:push` : `tests/push.mjs`, teste la logique de la fonction push (`supabase/functions/push/index.ts`) avec une base factice, et un vrai envoi web-push déchiffré comme le ferait un navigateur. Nécessite Node 22.18 ou plus (lecture du TypeScript).
- `npm run icons` : régénère `icons/*.png` depuis le SVG de `tests/icons.mjs`.

## Architecture

- `backend.js` expose `window.Backend` avec la même API pour deux implémentations : **Supabase** (si `config.js` est rempli) et **démo** (localStorage + BroadcastChannel, session par onglet dans sessionStorage). Les lignes gardent les noms de colonnes snake_case de `schema.sql`. La démo recopie les règles de lecture et d'écriture de `schema.sql` : toute règle modifiée dans le SQL doit l'être aussi dans `demoBackend`.
- `app.js` (IIFE, sections `// ---------- X ----------`) : état `S` (données) et `ui` (interface). `loadTable(nom)` recharge une table ; `subscribe` du backend appelle `queue(table)` qui recharge puis `route(true)`. Écrire = appel backend, puis `loadTable` de la table touchée. Les vues sont des fonctions `viewX()` qui renvoient du HTML ; la discussion garde son squelette et ne met à jour que ses parties (`renderChatParts`). Les champs `data-d="clé"` conservent leur brouillon dans `ui.draft` et le champ actif garde texte et curseur lors d'un rendu.
- Modèle : `payments` = un cumul par (tour, membre) avec `log` des versements ; `payouts` = remise d'un tour ; le tour courant est le premier sans remise. Un tour dure `interval_days` jours : il va de `start_date + tour × interval_days` à cette date + `interval_days` (5 jours à partir du 10 : du 10 au 15), le tour suivant commençant le jour où celui-ci finit (`roundStart`/`roundEnd` dans `app.js`). La **fin du tour est l'échéance** : cotisations dues, pénalités de retard et rappels (appli et fonction push) se calculent à partir d'elle. Chaque entrée de `log` est `{a, at, m}` où `m` est le moyen de paiement (clés de `METHODS` dans `app.js` ; absent sur les anciens versements). Un clic sur un nom de membre (`data-act="member"`) ouvre `memberDialog` (nombre et total des versements, par moyen). `paymentRows()` aplatit tous les `log` (historique du PDF et export CSV `exportCsv`, séparateur `;` et BOM pour Excel). Sujet « Général » = `topic_id` nul.
- **Connexion** : un seul champ « Numéro de téléphone » (une adresse tapée avec un @ reste acceptée pour les comptes antérieurs). `loginId()` (app.js) transforme un numéro en adresse privée `<chiffres>@tel.elongo.app` (0 initial → 243) ; `shownId()` la réaffiche en `+243…`. Mot de passe de 4 caractères minimum : Supabase en exige 6, donc `authPw()` complète un mot de passe plus court avec le suffixe `#elongo` avant l'envoi (inscription et connexion ; ne pas changer ce suffixe, il fait partie des mots de passe existants). Le déclencheur `supabase/phone-accounts.sql` (sur `auth.users`) confirme d'office ces comptes, qui n'ont pas de boîte e-mail ; il est hors de `schema.sql` car les tests locaux n'ont pas `auth.users`. Le numéro d'inscription préremplit le téléphone du formulaire d'invitation.
- **Suppression d'une tontine** (`act === 'deltontine'`, bloc « Supprimer la tontine » de `viewAdmin`, tout organisateur) : il faut taper le nom exact (`data-d="del.name"`). `B.remove('tontines')` supprime tout par les `on delete cascade` de `schema.sql` (la démo les recopie dans `B.remove`) ; les pièces jointes des messages chargés sont retirées du stockage au mieux. `afterTontineGone()` rouvre une autre tontine ou l'accueil ; les autres membres y passent aussi quand `loadTable('tontines')` ne retrouve plus la leur.
- **Rôles** : organisateur principal (`tontines.owner_id`) et co-organisateurs (`members.is_organizer`, membre actif avec compte). **Tous les organisateurs ont exactement les mêmes droits**, y compris nommer ou retirer un organisateur, supprimer la tontine et retirer le principal. En SQL, `is_owner(t)` = organisateur (principal ou co-organisateur), `is_creator(t)` = principal seul (ne sert plus qu'à `is_owner`) ; le déclencheur `guard_organizers` impose seulement qu'un organisateur ait un compte actif et n'autorise de changer `owner_id` qu'à un organisateur qui se met lui-même en principal. Retirer le principal (`act === 'rmprincipal'`, confirmation en deux clics) = `owner_id` passe à celui qui agit, puis la ligne de membre de l'ancien principal est supprimée : il perd l'accès (son appli retombe sur l'accueil via `afterTontineGone`). Côté appli : `isAdmin()` = organisateur, `isCreator()` = principal. La fonction push passe par `deps.isOrganizer`. La démo (`backend.js`) recopie ces règles. Après changement de `schema.sql`, l'utilisateur doit le relancer dans Supabase.
- **Calendrier** (`viewCal`, `calGrid`) : un tour couvre les jours `[roundStart, roundEnd[` ; le jour `roundEnd` d'un tour porte le badge de remise « T<n> » (c'est aussi le premier jour du tour suivant). Le mois affiché est `ui.calMonth`, borné du mois de `start_date` à celui de la fin du dernier tour. Les teintes alternent sur `r % 3`.
- **Versement** : `recordVersement(id, v, method)` est la seule voie d'enregistrement (fiche du membre `data-act="vers"` et fenêtre rapide `quickPayDialog` / `quickvers`) ; les erreurs s'affichent dans `#payErr` ou `#quickErr`. `removeVersement(mid, round, idx)` supprime une entrée de `payments.log` (n'importe laquelle, `idx = -1` pour une ligne sans journal), recalcule `amount`, `paid_on`, `done_on`, ne réécrit jamais les entrées `pending` côté serveur et inscrit « supprimé … saisi par erreur » au journal. Les fenêtres se redessinent via `ui.dlgFn` après une suppression (confirmation en deux clics, clé `dv:<membre>:<tour>:<index>` dans `ui.armed`).
- **Changer le bénéficiaire** (`swapDialog`, `act` `swap` / `swapdo` / `skipdo`) : l'ordre des tours est l'ordre des `members` par `position` ; `saveOrder(order)` renumérote tous les membres de 1 à n dans le nouvel ordre (écrit seulement ceux dont le numéro change), ce qui règle aussi les égalités de `position`. Seuls les tours `>= D.cur` non servis peuvent bouger ; les versements (`payments`) ne sont pas touchés puisque tout le monde cotise à chaque tour.
- **Hors connexion** (section « Offline » de `app.js`) : `selectCached()` lit le serveur et garde la réponse dans `localStorage` (`elongo.cache.<uid>.<tontine>.<table>`), la relit sans réseau ; inactif en démo (les données y sont déjà locales). Un versement saisi sans réseau devient une **opération** dans la file `elongo.queue.<uid>` (`{id, tid, round, member_id, a, m, at, ts, by, due, name}`), affichée par `overlayPending()` (entrées `pending` du `log`) ; `commitVersement(op)` relit la ligne côté serveur, ajoute l'entrée (identifiée par `op.id` : un second envoi est sans effet) et réécrit le cumul ; `syncQueue()` est appelée au retour du réseau, au démarrage, à chaque retour au premier plan et chaque minute. Une erreur réseau garde l'opération, une autre erreur la retire avec un message. Dans `tests/e2e.mjs`, `ctx.setOffline()` simule la coupure.
- **Rappel manuel** : `act === 'remind'` appelle la Edge Function `push` avec `{kind: 'remind', tontine_id}` (JWT de l'organisateur). `remindRound()` (dans `index.ts`) est partagée avec les rappels pg_cron et renvoie `{owing, notified, unreachable[]}` ; la limite de 3 h s'appuie sur le journal (`recentReminder`, entrées « Rappel envoyé… ») et sur `localStorage` côté appli. En mode démo `B.invoke` renvoie `null` : le test e2e le remplace.
- **Journal** : table `journal` (voir `schema.sql`) en insertion seule (pas de politique ni de droit de modification ou de suppression), lisible par les membres actifs, écrite par les organisateurs via `audit(texte)` dans `app.js` (silencieuse si la table n'existe pas encore). Les entrées de `payments.log` portent aussi `by` (qui) et `ts` (quand). `receiptText()` compose le reçu WhatsApp.
- **Thèmes** : `applyTheme()` pose `data-theme="light"`, `"dark"` ou `"black"` (sombre à fond noir pur, pour les écrans OLED) sur `<html>` (rien en mode automatique, où le CSS suit `prefers-color-scheme`) ; le choix est dans `localStorage` `elongo.theme` et un petit script de `index.html` l'applique avant le premier affichage. Les variables sombres sont écrites trois fois dans `styles.css` (media query, `:root[data-theme="dark"]` et `:root[data-theme="black"]`, qui ne change que les fonds) : les modifier ensemble. Pour du texte posé sur `--coin-tint`, utiliser `--on-tint`, `--on-tint-2` ou `--coin-text`, jamais une couleur codée en dur (illisible en sombre).
- **Récompenses** : `punctuality(m)` juge chaque tour déjà commencé à partir des `log` (`ok` payé en entier avant `roundEnd`, `late`, `missed` si terminé sans paiement complet ; un tour encore en cours et non payé n'est pas jugé). La série compte les `ok` consécutifs en partant du dernier tour jugé. Volontairement positif : aucun écran ne montre les retards d'un membre par ce biais.
- **Icônes** : les onglets du bas (`index.html`) utilisent des SVG en `currentColor` (classe `ti`) ; l'animation de l'onglet actif vise `svg:first-child`. Les émojis ne restent que dans le fil « Dernières nouvelles » du tableau en direct.
- **Discussion** : `msgHtml(m, prev)` rend une ligne `.mrow` (avatar, bulle `.msg`, heure, corbeille) ; deux messages du même auteur à moins de 5 minutes sont groupés, une **réponse** (`messages.reply` jsonb `{id, name, text}`, copie de l'auteur et d'un extrait : elle survit à la suppression du message cité) se lance par le bouton ↩ ou en glissant un message vers la droite (`startReply`, barre `#replyBox`, `ui.replyTo`) et se voit dans la bulle (`.quote`, clic = `gotomsg`), des **réactions emoji** (table `reactions`, clé `(message_id, user_id)` : une par personne et par message ; `reactionsHtml`, `act` `reactpick` / `react` : toucher son propre emoji le retire, un autre le remplace ; `loadTable('reactions')` est silencieux si la table n'existe pas encore), les **photos et vidéos** se joignent par le bouton 📷 (`#photoIn`, `act` `pickphoto`, `accept="image/*,video/*"`) ou 📎 ; une vidéo (`att.kind === 'video'`, limite `B.maxVideo` = 20 Mo en Supabase, alignée sur `file_size_limit` du bucket `lisanga`, jamais téléchargée sans appui sur « Voir la vidéo », pas de compression côté appli) s'affiche dans un `<video controls>` ; `autoLoadPhotos()` télécharge d'elles-mêmes les 12 dernières photos du sujet ouvert (`ui.attBusy` évite de réessayer en boucle un échec ; le bouton « Afficher la photo » reste en secours) et un appui ouvre `zoomimg` (grande photo + « Enregistrer la photo »), un séparateur `.dsep` s'affiche à chaque nouveau jour. Le formulaire de nouveau sujet (`#topicForm`) n'apparaît qu'après un clic sur `data-act="newtopic"` (`ui.newTopic`). Les éléments du panneau doivent pouvoir rétrécir (`min-width: 0`, `minmax(0, 1fr)`) sinon la page déborde sur le côté.
- **Fiche de versement** (`payDialog`, `data-act="manage"`) : les saisies de versement (`input[data-d="v.<id>"]`, `select[data-d="m.<id>"]`) vivent dans la fenêtre modale, pas dans la liste. Les erreurs de saisie s'affichent dans `#payErr` (le toast est caché sous la fenêtre) ; la fiche se ferme après un versement ou une annulation. Dans `tests/e2e.mjs`, `openPay(nom)` ouvre la fiche d'un membre.
- **Animations** : `celebrate()` (confettis), `buzz()` (vibration), classe `enter` sur `#view` à chaque changement d'écran (retirée après 900 ms pour ne pas rejouer l'animation à chaque mise à jour en direct), barre de cagnotte animée depuis `ui.potPct`. Tout respecte `prefers-reduced-motion`. Dans `tests/e2e.mjs`, `shot()` attend 1 s la fin des animations : ne pas l'appeler entre un déclencheur de toast et son attente (le toast dure 3,2 s).
- **Rapport d'un jour** (`dayDialog`) et coches du calendrier (`roundDone`) : `roundDone(c, r, rows)` renvoie la date à laquelle tous les membres actifs avaient versé la cotisation du tour `r` (cumul des `log` de `paymentRows()`), ou `null`. Les jours du tour à partir de cette date sont cochés (`.cd.paid`). Le rapport d'un jour montre les tours qui finissent ce jour-là, qui ont reçu un versement ce jour-là ou qui sont en cours.
- **Annulation d'une remise** : supprimer la ligne `payouts` du tour (`act === 'undo'` pour le dernier tour, `unserve` pour un tour donné ; confirmation en deux clics via `ui.armed`). Les `payments` ne sont pas touchés ; le tour courant redevient le premier sans remise.
- **Liaison compte / membre** : un membre ajouté à la main n'a pas de `user_id`. À l'acceptation d'une demande (`act === 'accept'`), le choix « C'est : <nom> » supprime la ligne `pending` puis met son `user_id` sur la ligne existante (deux requêtes : la contrainte `unique (tontine_id, user_id)` interdit de faire les deux en une), et recopie le téléphone si la ligne n'en avait pas.
- **Code de déverrouillage** (section « Unlock code » de `app.js`) : verrou d'écran local par appareil et par utilisateur, `localStorage` `elongo.lock.<uid>` = `{salt, hash, len}` (SHA-256 salé, jamais le code). Pas de table ni de règle SQL. « Code oublié » efface le code et déconnecte.
- Pièces jointes : bucket privé `lisanga` (nom technique gardé de l'ancien nom du projet : ne pas le renommer sans migrer le stockage), chemin `<tontine>/<user>/<fichier>`, message → `att {path,name,type,size,kind}`.

- **Notifications push** : l'appli (`enablePush`/`disablePush`) enregistre l'appareil dans `push_subscriptions` ; après un versement, une remise ou un message, `notify()` appelle la Edge Function `push` (`B.invoke`), qui recompose le texte depuis la base (le client n'envoie jamais de texte libre), vérifie les droits (organisateur pour versements et remises, auteur pour un message) et envoie avec web-push. Les rappels quotidiens (pg_cron, `supabase/push-cron.sql`) sont facultatifs et ne sont pas activés en production ; l'appli ne les annonce pas. `sw.js` affiche la notification (rien si l'appli est au premier plan) et ouvre le bon onglet au clic. Le texte des notifications est dans `index.ts` ; les clés VAPID privées ne vont jamais dans le dépôt.

## Points d'attention

- Toute donnée saisie injectée dans le HTML passe par `esc()`.
- Après modification d'un fichier listé dans `ASSETS` de `sw.js`, incrémenter `VERSION`.
- Changer le schéma : modifier `schema.sql` (rejouable), `demoBackend`, et ajouter un cas dans `tests/rls-check.sql`.
- L'adaptateur Supabase est vérifié en réel pour la connexion, l'inscription et la création de tontine ; le partage en direct, les fichiers et l'envoi des notifications push se vérifient avec deux téléphones (rien de tout cela ne peut tourner dans l'environnement de développement, sans accès réseau à Supabase).
